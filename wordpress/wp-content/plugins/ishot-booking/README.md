# iShot Booking (WordPress plugin)

Booking management for the iShot Concept studio: availability, conflict-safe bookings, deposits and notifications. This is Phase 2 of the implementation plan.

## How double bookings are prevented

1. A booking's session is widened by its buffers (`NewBooking::blockedRange()`).
2. That range is mapped onto fixed slot units, 30 minutes by default (`Domain\SlotUnits::cover()`). Any unit the range touches counts.
3. `Persistence\BookingRepository::create()` inserts the booking row and one `ishot_slot_locks` row per unit in a single InnoDB transaction.
4. The lock table's primary key `(resource_id, unit_start_utc)` makes MySQL reject a unit that is already held. The transaction rolls back and the caller gets a `SlotConflict` (HTTP 409). Under contention, InnoDB can instead roll one racer back as a deadlock victim; the repository re-runs that transaction (up to 3 attempts, with jitter), and the retry then sees the winner's locks and ends in a clean `SlotConflict`.
5. Statuses that release a booking (cancelled, expired, completed, no-show) delete its lock rows in the same transaction as the status change.

The UI's availability (`Domain\Availability`) is advisory; the insert is the only authority. `tests/Integration/ConcurrencyTest.php` releases 50 separate processes at the same instant against overlapping times and asserts exactly one booking.

## Development

Requires Docker. From the repository root:

```sh
npm run wp:start      # WordPress dev site on :8888, test site on :8889
npm run wp:setup      # composer install inside the test container (first time)
npm run test:php      # all PHP tests
npm run test:php:unit # domain tests only (fast)
```

Dev site login: `admin` / `password`.

**Email locally:** `npm run mail:start` runs [Mailpit](https://mailpit.axllent.org/) (inbox at http://localhost:8026). The development site sends all mail there through `wordpress/dev/mu-plugins/ishot-mailpit.php`, which `.wp-env.json` maps into the development environment only; the test site keeps WordPress's mock mailer. To send every lifecycle email at once:

```sh
npx wp-env run cli wp eval-file wp-content/ishot-dev/notification-smoke.php
```

The script books as `*.smoke@example.com` clients and runs reminders and hold expiry at simulated times, so other pending dev bookings in those windows are also reminded or expired.

**If `wp-env start` says the network is unavailable:** wp-env checks connectivity with a raw DNS query. On machines where Node's resolver points at a local address with no DNS server behind it, preload a shim that routes `dns.resolve` through the OS resolver:

```sh
NODE_OPTIONS="--require /path/to/dns-lookup-shim.cjs" npm run wp:start
```

## Public API (`/wp-json/ishot/v1`)

| Route | Notes |
|---|---|
| `GET /services` | Bookable services: id, title, duration, from-price, deposit |
| `GET /availability?service=&date=YYYY-MM-DD` | Free studio-local start times (`H:i`) for that day; `Cache-Control: no-store` |
| `POST /bookings` | Body: `service`, `start` (`YYYY-MM-DDTHH:MM`, studio time), `name`, `email`, `phone`, `location`, `notes`, `consent: true`, `website` (honeypot, leave empty). Optional `Idempotency-Key` header. |

`POST /bookings` responses:
- **201**: `{status, start, end, token}`. The token is the client's manage-booking secret. Only its SHA-256 hash is stored.
- **200** `{replayed: true}`: a retry with the same Idempotency-Key. No new booking is created.
- **202**: the honeypot was filled. Nothing is stored.
- **400**: invalid fields.
- **409** `ishot_slot_taken`: `data.alternatives` lists up to 3 of the nearest free starts.
- **422** `ishot_too_soon | too_far | misaligned | outside_hours | unknown_service`
- **429**: rate limited. The default is 10 requests per 10 minutes per address; change it with the `ishot_booking_rate_limit` filter.
- **503** `ishot_busy`: every retry lost a database deadlock while the time was still free. Nothing was stored; send the same request again (with the same Idempotency-Key).
  The response carries `Retry-After: 2` (also `data.retry_after`) and never the database's own error text.
  Retries are bounded (3 attempts with jitter, each rolled back first). After the last one the repository
  re-checks before answering: a same-key twin that committed meanwhile is returned as that booking (no 409
  for a request that succeeded), a time taken by someone else is 409 `ishot_slot_taken` with alternatives,
  and only a time that is still free is 503. In wp-admin the same case shows the notice "The calendar is busy
  right now…" (bulk runs report busy bookings separately and say to try them again), and the hold-expiry
  sweep leaves a busy hold for its next run.

### Database contention: what is guaranteed

- **All or nothing.** Every write inside a booking change (create, status change, move, block/unblock),
  and its COMMIT, is checked. If any statement fails, the whole change is rolled back and retried
  (deadlock or lock wait) or reported as an error (anything else). A change is never reported as saved
  unless its COMMIT succeeded on the connection it started on.
- **Bounded waits.** Inside a booking change each statement waits at most 5 s for a row lock (filter
  `ishot_booking_lock_wait_timeout`; 0 keeps the server's own setting), and the session's previous value
  is restored afterwards. A change usually finishes in milliseconds. In the worst case (every statement
  of every attempt waiting the full time) a request takes about 30-45 s: still inside common PHP and
  proxy limits, so the client gets the 503 rather than a timeout.
- **Error classification** uses the MySQL error number (1213 deadlock, 1205 lock wait timeout, 1062
  duplicate key), so it works whatever language the server's messages are in.
- **Hold expiry** skips a hold it cannot expire right now and carries on with the rest: a busy hold, one
  that staff or the client changed at the same moment, and one that fails for any other reason. Only that
  last kind fires `ishot_booking_hold_expiry_failed` (booking id, exception; id 0 when the safety net
  below fails). Every skipped hold is tried again on the next request or five-minute sweep.
- **Safety net.** The five-minute sweep also frees lock rows whose booking is gone or no longer holds a
  slot (`BookingRepository::releaseOrphanLocks()`), so a time can never stay unbookable for good.
- **Lost connections.** While a change runs, wpdb's automatic reconnect is switched off. If the database
  server drops the connection mid-change, the request fails (WordPress's database error page, or an error
  from the plugin once a page has started rendering) and the server rolls the whole change back; nothing is
  half-saved and nothing is reported as saved. (Without this,
  wpdb would re-run the failed statement outside the transaction.)
- **Database drop-ins with several servers** (HyperDB, LudicrousDB with read replicas): every query of
  this plugin must go to the primary (with HyperDB, enable `srtm`), because slot locking relies on
  `SELECT … FOR UPDATE` inside a transaction. On such sites the connection check is off by default
  (filter `ishot_booking_connection_guard`).

## Staff API (`/wp-json/ishot/v1/staff`, signed in; wp-admin sends `X-WP-Nonce`)

| Route | Capability |
|---|---|
| `GET /bookings?from=YYYY-MM-DD&to=YYYY-MM-DD` | `view_ishot_calendar`. The end date is exclusive; at most 62 days per request. |
| `GET /bookings/{id}` | `view_ishot_calendar`. Includes the audit timeline (who did what, when). |
| `POST /bookings/{id}/actions` `{action, version, start?, deposit_amount?, note?, reason?}` | `confirm` / `complete` / `no_show` need `edit_ishot_bookings`; `request_deposit` / `deposit_received` / `cancel` / `reschedule` need `manage_ishot_bookings` |
| `POST /blocks` `{start, end, reason}`, `DELETE /blocks/{id}` | `block_ishot_time` |

Staff actions are not bound by client policy (notice period, opening hours). They are still bound by slot exclusivity.

Error responses:
- **401**: signed out.
- **403**: missing the capability.
- **404**: unknown booking.
- **409** `ishot_stale`: someone else changed the booking first. Reload and retry with the new `version`.
- **409** `ishot_slot_taken`: the new time clashes with another booking or block.
- **422** `ishot_invalid_transition`: for example, completing a booking that was never confirmed.
- **503** `ishot_busy` (`Retry-After: 2`): any change (confirm, cancel, deposit, complete, no-show, reschedule, block, unblock) whose every retry lost a database deadlock or lock wait, and, for a move, while the new time was still free. Nothing changed; try again.

**Reschedule:** the old slots are released and the new ones claimed in one transaction. On a clash, the rollback leaves the booking exactly where it was.

## Client manage-booking link (`/wp-json/ishot/v1/manage`)

The 64-character token from `POST /bookings`, or from any client email, is the client's only credential. Only its hash is stored.

**URL convention (`src/Frontend/ManageUrl.php`):** every link is `https://<site>/manage-booking/#token=<token>`.
- **The token stays in the URL fragment.** Browsers never send fragments to servers, so the token never reaches access logs, proxies, analytics or `Referer`.
- **How the page uses it:** it reads `location.hash` and calls `GET`/`PATCH /wp-json/ishot/v1/manage` with the token in the **`X-Ishot-Manage-Token` header**. It then clears the hash with `history.replaceState`.
- **The page itself** is served with `Referrer-Policy: no-referrer`, `Cache-Control: no-store, private` and `X-Robots-Tag: noindex`.
- **Backward compatibility:**
  - Links already emailed (`/manage-booking/#token=…`) keep working, including the per-email tokens in `ishot_booking_links`.
  - Older shapes, `/manage/<token>` (the prototype's) and `/manage-booking/?token=<token>`, get a 302 to the fragment form with the same privacy headers.
  - `GET`/`PATCH /bookings/{token}` still answers. It's **deprecated** because the token sits in the path: responses carry `Deprecation: true` and a `Link` to `/manage`. Remove it once the Phase 3e page ships.

- **`GET`:** shows the status, service, times, deposit, `change_deadline`, `can_cancel` and `can_reschedule`.
  - No email or phone is shown, so a forwarded link doesn't leak contact details.
  - Responses are sent with `Cache-Control: no-store` and `X-Robots-Tag: noindex`.
- **`PATCH {action: "cancel"}`** or **`{action: "reschedule", start: "YYYY-MM-DDTHH:MM"}`:**
  - Allowed only while the booking holds a slot, and before `cancel_cutoff_hours` (default 72) ahead of the session.
  - A reschedule must satisfy the same policy as a new request, and a clash returns 409 with alternatives.
- **Errors:**
  - unknown tokens: **404**, never 403
  - after the cut-off: **422** `ishot_past_cutoff`
  - a cancel or reschedule whose every retry lost a database deadlock or lock wait (for a reschedule, while the new time was free): **503** `ishot_busy` with `Retry-After: 2` (nothing changed; try again)
  - cancelled or finished bookings: **422** `ishot_not_changeable`
- **Link lifetime:** the link stops working 30 days after the session.
- **Rate limit:** 30 requests per 10 minutes per address. Change it with the `ishot_booking_manage_rate_limit` filter.

## Hold expiry

Unpaid `requested` and `pending_deposit` bookings hold their slot until `hold_expires_at` (`hold_hours` after the request, default 48). Lapsed holds become `expired` and their slots are freed in two ways:
- **Lazily**, before every availability read, booking request and manage-link request. A lapsed hold never blocks anyone, even if cron is late.
- **By a five-minute WP-Cron sweep** (`ishot_booking_expire_holds`). On production, set `DISABLE_WP_CRON` and run `wp cron event run --due-now` from a system cron every minute.

Confirming a booking clears its hold.

## Notifications

**Only committed changes send email.** `BookingRepository` writes the audit event and the emails it calls for (`Notifications\Rules`) into `ishot_notifications` inside the same transaction as the booking change. A rollback (slot conflict, stale version, deadlock retry) leaves no email behind. A `UNIQUE dedupe_key` (`e{event}:{template}`, or `{template}:{booking}:{time}` for reminders) makes queuing an email twice impossible. Each row stores a snapshot of what the email prints, without the token hash, phone or notes.

**Delivery** (`Notifications\Dispatcher`, run by Action Scheduler):
- After `COMMIT`, a unique async job (`ishot_booking_send_notifications`) drains the outbox. A recurring job every five minutes (`ishot_booking_notifications_tick`) requeues abandoned sends, queues timed reminders and sends anything due. Even if an async job is lost, nothing waits longer than one tick.
- A row is claimed with a conditional `UPDATE … WHERE status = 'pending'`. Only the worker that changed the row sends it.
- A failure is retried after 5 min, 15 min, 1 h and 4 h. After the 5th attempt the row is `failed`, and a `notification_failed` event appears in the booking's history. Stored errors have email addresses and tokens redacted.
- Emails about one booking to one recipient go out in order. A later email waits while an earlier one is still pending.
- A claim left by a worker that died mid-send is requeued after 15 minutes. In that one case delivery is at-least-once, so the client may get the email twice.

| Template | To | When |
|---|---|---|
| `request_received`, `new_request` | client, studio | Request created |
| `deposit_requested` | client | Staff ask for a deposit (amount plus the studio's instructions; nothing is marked paid) |
| `deposit_reminder` | client | Deposit still unpaid 24 h before the hold lapses (not within 12 h of asking) |
| `hold_expiring` | studio | Unanswered request 12 h before its hold lapses |
| `confirmed` | client | Confirmed, with an `.ics` REQUEST. Says the deposit was received only when staff recorded it |
| `rescheduled`, `client_rescheduled` | client, studio (only if the client moved it) | Moved. Updated `.ics` if confirmed |
| `cancelled`, `client_cancelled` | client, studio (only if the client cancelled) | Cancelled. `.ics` CANCEL if it had been confirmed |
| `hold_expired`, `hold_expired_studio` | client, studio | Hold lapsed |
| `reminder` | client | 24 h before a confirmed session (again after a move) |
| `thank_you` | client | Marked completed |

**Calendar files:** one UID per booking (`booking-{id}@{site host}`), and `SEQUENCE` equals the booking's `version`, which grows with every change. Calendar apps therefore move or remove the existing event rather than adding a duplicate.

**Manage links:** every client email gets a freshly minted token. Only its SHA-256 hash is stored, in `ishot_booking_links`. The token travels in the URL fragment (`/manage-booking/#token=…`), which browsers never send to servers or put in `Referer`. Links from earlier emails keep working. A link whose email was never delivered is revoked.

**Settings** (Bookings → Emails, `manage_ishot_settings`): sender name and address, Reply-To, studio notification address, currency, deposit instructions, the manage page URL, and per template an on/off switch, subject and opening paragraph. Booking details and links are always added, so an edit cannot drop them. The HTML uses the design tokens from `assets/email/theme.json`, and every email has a plain-text alternative. Delivery goes through `wp_mail()`, so production should use an SMTP plugin with SPF, DKIM and DMARC set up on the domain.

**Staff calendar feed:** `GET /wp-json/ishot/v1/calendar.ics?key=…` lists the last 30 and next 365 days of live bookings (requests as TENTATIVE) and blocked time. It holds client names but no email addresses or phone numbers. The key is created on the Emails screen, shown once, and stored only as a hash. A wrong key gets 404. Creating a new key revokes the old URL. The feed is rate-limited to 60 requests per hour per address (`ishot_booking_feed_rate_limit`).

## Deposits and payment gateways

Deposits are offline for now: Stripe does not serve Liberia. `ManualGateway` prints the studio's deposit instructions (Bookings → Emails) in the deposit emails. When staff press **Mark deposit received** they can add a payment reference, such as a mobile-money transaction ID. The booking records `deposit_gateway` (`manual`) and `deposit_reference`; the REST API returns both under `deposit`.

Adding a gateway later (PayPal, mobile money) needs no schema change. Implement `IShot\Booking\Payments\PaymentGateway` and return it from the `ishot_booking_payment_gateway` filter.

## Privacy

- **Export / erase:** the plugin registers with Tools → Export Personal Data and Erase Personal Data. A client's bookings match by the email they booked with, or by their WordPress account.
- **What erasure does:** past or cancelled bookings are anonymised. That clears the name, email, phone, location, notes, account link, payment reference and public token. It also deletes the booking's queued and sent email snapshots and every manage link, and strips note and reason text from the audit log. Date, service, status and deposit amount are kept for the studio's accounts. An `anonymised` audit event records it.
- **What erasure keeps:** upcoming live bookings (requested, awaiting deposit, confirmed). The erasure screen says which ones and why; cancel them first, or erase again after the session.
- **Retention:** a daily Action Scheduler job (`ishot_booking_retention`) anonymises bookings whose session ended more than **Keep client details** months ago (Bookings → Settings; default 24; 0 turns it off).
- **Policy text:** suggested wording is added to Settings → Privacy → Policy guide.

## Importing the prototype content

```
npm run wp:import            # exports the seed, then imports into the dev site
wp ishot import-prototype --seed=<prototype-content.json> --images=<dir> [--dry-run] [--force] [--publish]
```

- `npm run seed:export` writes `wordpress/seed/prototype-content.json` from the React app's `src/data.js`, `src/assets.js` and the sample projects. It contains 7 categories, 6 photos (alt text, focus point, portfolio order), 6 services and 2 projects.
- Images are the prototype's 2400px WebP files (`public/images/opt`). WordPress generates the other sizes.
- **Never imported:**
  - testimonials (none are real yet);
  - journal posts and bookings (sample copy);
  - prices and deposits (owner to supply), so services are never made bookable;
  - contact details.
- **Repeatable:** each item carries an import key, so a re-run never duplicates anything. Items unchanged since the last import are updated when the seed changes. Items edited in WordPress are kept and reported, unless you pass `--force`.
- **Drafts by default:** new posts are drafts unless you pass `--publish`. A re-run never changes a post's status. An item with the same slug created by hand is adopted and treated as edited, so it is not overwritten.

## My bookings (`GET /wp-json/ishot/v1/me/bookings`)

For signed-in client accounts (`read_own_ishot_bookings`).
- **Signed out:** 401. **Any other role:** 403.
- **Always scoped to the caller:** no parameter can name another user. The list holds:
  - bookings linked to the account;
  - unclaimed guest bookings under an email address the account has **verified**, meaning it set its password from the emailed link. Verification is tied to the address, so changing the account email withdraws access until the new address is verified.
- **Parameters:** `page`, `per_page` (1-50, default 10), `when` = `all|upcoming|past`.
- **Response:** totals in the `X-WP-Total` and `X-WP-TotalPages` headers, `Cache-Control: no-store, private`. No token hashes, idempotency keys or versions.

## Optional client account at booking time

`POST /bookings` accepts `create_account: true`. Guests can still book without it.
- **Signed-in client:** the booking is linked to their account (`"account": "linked"`). Bookings made by signed-in staff are never linked to the staff account.
- **Guest asking for an account:**
  - **Unused email:** an `ishot_client` account is created with a random password, and WordPress emails a set-your-password link. Nobody is signed in, and the username isn't the email address.
  - **Email that already has an account:** nothing is created, linked or emailed.
  - Both cases answer `"account": "check_email"`, so the form can't be used to find out who has an account.
- **Limits:** 3 account requests per address per hour (`ishot_booking_account_rate_limit`); above that the booking still succeeds with `"account": "not_created"`. No account is made for honeypot hits, policy rejections or clashes. Turn the feature off with `ishot_booking_client_accounts` → false.

## Contact form (`POST /wp-json/ishot/v1/contact`)

Replaces Web3Forms, so no third-party form key is published.
- **Fields:**
  - `name` (1-100)
  - `email`
  - `phone` (optional, ≤30)
  - `enquiry` (optional, ≤100)
  - `message` (10-2000)
  - `consent: true` (required)
  - honeypot `website`
- **Responses:** **202** `{"status":"received"}`, also returned to bots, which have nothing stored. **400** on invalid input. **429** above 5 per 30 minutes per address (`ishot_booking_contact_rate_limit`).
- **Delivery:**
  - Stored first in `ishot_enquiries`, then emailed to the studio address with `Reply-To` set to the sender, so a mail outage delays an enquiry but never loses it.
  - Failed sends retry after 5, 15, 60 and 240 minutes, then the enquiry is marked `failed`.
  - **Bookings → Enquiries** (managers) lists every enquiry and flags failures.
  - Nothing is emailed to the address typed into the form, so it can't be used as a spam relay.
- **Privacy:** enquiries appear in Export Personal Data, are deleted by Erase Personal Data, and are purged by the retention job after **Keep client details** months.

## Bulk actions and CSV export (Bookings → All bookings)

- **Bulk actions:** Confirm, Mark completed, Mark no-show (photographers and managers), and Cancel (managers).
  - Each booking is checked with the same rule as its detail screen: lifecycle, "only after the session started" for complete and no-show, and capability. Ineligible bookings are skipped and reported, never forced.
  - At most 100 per run. The list form posts with the `bulk-bookings` nonce, and the result is shown after a redirect.
  - Every change goes through `StaffActions` and is audited with `bulk: true`.
  - Deposit received (needs a payment reference) and reschedule (needs a time) are not offered in bulk.
- **Export CSV:** managers only (`manage_ishot_bookings`), behind a nonce, following the current filters.
  - Columns: booking, status, service, start/end, client, email, phone, location, deposit, deposit status, payment reference, requested.
  - Notes, token hashes and keys are left out.
  - Cells starting with `= + - @`, tab or carriage return are prefixed with `'` (formula-injection guard).
  - Each export is logged in the `ishot_booking_export_log` option: who, when, how many rows, which filters.
